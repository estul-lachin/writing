INC-001: Bait account compromised, cryptominer dropped

Honeypot #2 · Incident date 2026-11-14 (UTC) · Analyst: Estul Lachin

Final report · updated 2026-11-16 · 48-hour observation closed 2026-11-16 03:00 UTC

Summary

At 00:40 UTC on 2026-11-14 a brute-force bot guessed the bait account admin / admin on Honeypot #2. Two hours later a second botnet stage reused the credential, pushed in the cryptominer .dhpcd and set up three kinds of persistence (cron, SSH keys, a changed password). The attacker never gained root, and no outbound connection succeeded: two layers of egress control blocked the mining pool, C2 and downloads, so the miner only burns CPU.

A 48-hour observation followed. The backdoor SSH key came back three times, from three different IP addresses; each visit only looked around (hardware, running processes, whether the key still worked). There was no new payload, no new persistence and no root. A new rule, 100213, turned every key login into a High incident automatically. The host was not cleaned: it moves into phase 2 of the honeypot with a different weak bait password and will be rebuilt from a clean image afterwards.

The intrusion was found during a manual review of rule_level >= 10 events in Sentinel: one Wazuh 40112 ("Multiple authentication failures followed by a success", level 12) from 121[.]167[.]150[.]214 against admin. At that time no analytics rule existed for Honeypot #2, so time from compromise to discovery was about 2 hours.

The miner itself kept running in the background session that started it on 11-14:

  • Cron relaunched .dhpcd every hour at :35 for the full 48 hours.
  • At 02:36:47 on 11-16 it restarted itself once, outside the cron schedule.
  • At 04:06:09 on 11-16 it ran /sbin/modprobe msr allow_writes=on. XMRig does this to unlock CPU model-specific registers for faster RandomX mining. Running as uid 1001, it cannot succeed. It came one second after the 04:06:08 login, but the logs show no link between the two.

What did not happen: no change to cron or authorized_keys (rule 100211 fired only on 11-14, rule 100212 only on our own test); no rule 100200; every attacker command ran as uid and euid 1001. The uid 0 entries at each login are sshd running the login banner scripts as root, which is normal.

Impact assessment

The attacker never gained root and sent no traffic out. Real impact is limited to the admin account's privileges and the victim's CPU and memory.

Privilege escalation: none. The evidence comes from auditd records stored on the gateway, which the attacker cannot alter:

  • chattr, rm and mv all ran with euid 1001. The guest agent binaries are still present (dated Oct 21), and dpkg -V procps passwd google-guest-agent reports no changes.
  • passwd shows euid 0 because it is a SUID-root program; it checks the real uid before changing anyone else's password, so this is not evidence of escalation. The attacker could only change its own admin password; ubuntu, test and the other targets do not exist on the host.
  • /etc/shadow carries only the normal ext4 e attribute; chattr +a never took effect.

Egress: none. Between 02:35 and 15:36 the tripwire blocked 10,785 outbound attempts. Not one succeeded:

Response and evidence handling

Decision: observe, do not clean up. A honeypot's value is seeing what the attacker does next, and every safety boundary held: no root, two layers of egress blocking, logs off the host.

  1. Read-only triage. Logged in over the WireGuard management channel and used only read-only commands (who, ss, ps, ls, journalctl). The command history came from Wazuh alerts on the gateway, not from ausearch on the victim.
  2. Evidence preservation. Two archives of /home/admin, the cron spool and /tmp/tmp.* were copied to the gateway and hashed. They are never extracted or executed.
  3. Protect the monitoring. All five Wazuh agent processes run with oom_score_adj=-900 (persisted with a systemd drop-in); the management sshd already runs at -1000.
  4. Keep the state for 48 hours. The changed admin password stayed in place so this group's return pattern could be observed. Completed 2026-11-16 03:00 UTC; see Observation period.

Disposition: not cleaned, kept for phase 2, then rebuilt. On 2026-11-16 the admin password was reset to another common weak password from public wordlists, so new attackers can get in too. The miner, the cron entry and the backdoor keys stay in place, so the original group can still log in. When phase 2 ends, the victim is rebuilt from a clean image against the recorded baseline instead of being cleaned in place.

Detection improvements

All four gaps were fixed the same night, a Sentinel analytics rule went live, and a controlled cron change verified the whole chain. The next day added detection for the backdoor key and the bait home directory. The next attacker who logs in with a harvested password now raises a High incident within about 25 minutes.

The threshold moved from the planned 10 to 12: rule 2502 (level 10) fires about every 7 minutes from constant scanning and would have raised about 200 incidents a day.

The self-test also showed:

  • Latency: an event reaches Sentinel in about 9.5 minutes and becomes an alert about 12 minutes later, about 25 minutes end to end.
  • Duplicate alerts: one record was caught by two consecutive runs near a window edge; entity grouping merged them into a single incident. Since fixed with an upper bound on the window.
  • Playbook: the enrichment playbook ended as Cancelled after 254 ms on this incident, which has no IP entity. That matches its "skip when there is no IP" design.

Processes started by cron are also logged: Debian's cron goes through PAM, and pam_loginuid sets the audit uid to 1001, which matches the auditd rule auid>=1000.

Lessons learned

In a honeypot, a successful login to the bait account is itself the highest-priority signal. It must not depend on an indirect pattern such as "failures followed by a success".

What worked

  • Two layers of egress control held against a real attack: the miner runs, but not one packet got out.
  • Logs off the host: the privilege-escalation verdict rests on auditd records stored on the gateway, out of the attacker's reach.
  • FIM whodata named the exact process, user and change (mktemp → crontab → rm).
  • Isolation followed predefined triggers instead of pulling the plug on sight.
  • Rule 100213, added during the observation, paid off at once: every backdoor-key visit became a High incident without anyone watching.

What to improve

  • Discovery relied on manual review and took about 2 hours. An analytics rule now covers it.
  • Test new rules against real log samples: the first version of 100210 matched only Accepted password and would have missed keyboard-interactive logins.
  • Do not judge escalation by euid alone: SUID programs such as passwd always run with euid 0.
  • Egress blocking does not stop inbound pushes: the payload came in over SCP inside the attacker's own SSH session, with no download from the victim. Catching a payload landing needs inbound-side detection (FIM, rule 92603).
  • A noise budget must respect priority: repeated tripwire noise could crowd high-severity alerts out of the daily upload budget, so level 10+ alerts are now exempt.
  • Changing the password does not evict this attacker: the planted key is shared by at least three IPs. In a real environment, response must remove authorized_keys entries and cron jobs too.

Next steps

  • Done: the observation period closed, the findings are in this report, FIM now covers /home/admin (rule 100212), and phase 2 started with a new weak bait password.
  • Look up the .dhpcd SHA256 on VirusTotal (hash only, no upload) to confirm the miner family.
  • Map ATT&CK tactics per Wazuh rule in the analytics rule, instead of the static list every alert carries today.
  • Tag tripwire logs with the owning process, to separate miner traffic from the system's own.
  • When phase 2 ends, rebuild the victim from a clean image against the recorded baseline.
